# Opus 実装指示書: 評価スコアのグラデーション調整

この指示書に従って、restaurant evaluator のスコアが 0 / 1 に寄りすぎる問題を**小さく調整**してください。

## 目的
現状の live 評価では、mock よりもスコアがくっきりしやすい傾向があります。
これは主に以下の組み合わせによるものです。

- 候補データがまだ薄い
- normalizer により候補属性がかなり離散化されている
- evaluator prompt に「中間値をどう使うか」の指示が弱い

今回は大きな設計変更はせず、**まず evaluator prompt のみを微調整**して、
部分一致・弱い一致・情報不足のときに中間値が出やすくしてください。

---

## 今回の方針
### やること
- `evaluate_candidate` 系プロンプトにスコア帯域ガイドラインを追加する
- `unknown` と低スコアを混同しないように明記する
- 軸ごとの score が必要以上に 0.0 / 1.0 に張り付かないようにする
- テストや README を必要最小限だけ更新する

### やらないこと
- aggregate ロジックの変更
- hard_constraint_violation の意味変更
- normalizer の変更
- LLM モデルの変更
- restaurant 以外のドメイン拡張

## 1. スコア帯域ガイドラインを追加
prompt に、少なくとも以下の趣旨を明記してください。

### 基本方針
- score は 0.0〜1.0 の連続値
- ただし、**明確な根拠がない限り極端値 0.0 / 1.0 を多用しない**
- 完全一致でも通常は 0.85〜0.95 程度を目安にする
- 部分一致は中間値を使う
- conflict は低スコアだが、hard violation でない限り必ずしも 0.0 ではない
- 情報不足は `unknown` を使い、無理に 0.0 や 0.5 を付けない

### 推奨帯域
以下は厳密ルールではなく目安として prompt に入れてください。

- 強く一致: `0.80〜0.95`
- 部分一致: `0.45〜0.75`
- 弱い一致: `0.20〜0.40`
- conflict だが hard violation ではない: `0.05〜0.25`
- `unknown`: score を作らず、status を `unknown`

### 注意
- 「完全一致は必ず 0.9」などの固定値ルールにはしない
- あくまで帯域で誘導する
- 疑似精密さを避けるため、根拠のない細かい差を作らない

## 2. 軸別の追加ガイド
restaurant 評価では、軸ごとに中間値が必要になるので、必要なら以下の例を prompt に追記してください。

### atmosphere
- 明示的に静か・落ち着いている → 高得点
- 一部だけ示唆がある → 中間値
- 賑やか → conflict / 低得点
- 情報がない → `unknown`

### budget
- 予算内でかなり近い → 高得点
- 少し上振れ / 少し下振れ → 中間値
- 明確に大きく外れる → 低得点または hard violation
- 情報がない → `unknown`

### location
- 同一エリア → 高得点
- 隣接 / 近接エリア → 中間値
- 離れている → 低得点
- 情報がない → `unknown`

### genre / cuisine
- 明確に一致 → 高得点
- 近いが同一ではない → 中間値または conflict
- 明確に違う → 低得点
- 情報がない → `unknown`

重要なのは、**部分一致のときに中間値を使うことをモデルに明示すること**です。

---

## 3. unknown と low score を分ける
prompt に、次をはっきり書いてください。

- 情報不足は `unknown`
- `unknown` は不一致ではない
- 情報が無いのに `score=0.0` を付けない
- `score` を付けるのは、少なくとも何らかの適合 / 不適合判断ができるとき

これは既存設計と整合します。

---

## 4. reasons も少し改善
score だけでなく `reason` の記述も、二値断定に寄りすぎないようにしてください。

推奨:
- 「完全に一致」ばかり使わない
- 「部分的に合致」
- 「近接エリアのため一定の適合」
- 「価格帯はやや上振れ」
- 「情報不足のため判断保留」

のような表現を許容する

ただし schema は壊さないでください。

---

## 5. テスト要求
最低限、以下のどれかを追加または更新してください。

### A. prompt snapshot / prompt content test
- 新しい帯域ガイドが prompt に含まれていること

### B. evaluator unit test（可能なら）
- LLM 呼び出しモックを使い、prompt に新ガイドが埋め込まれていることを確認

### C. docs 更新
- mock は設計的な固定値、live は帯域ガイドで誘導されることを README か docs に一言追記

今回、実 LLM 応答の統計検証までは不要です。
まずは prompt の契約を固定してください。
